# Stripe External 3DS Request Parity

## Objective

Make Stripe Authorize requests generated by UCS preserve completed external
3DS authentication data in the same way as Hyperswitch. This resolves shadow
request differences where Hyperswitch submits Stripe's external-3DS fields but
UCS instead submits `payment_method_options[card][request_three_d_secure]`.

The implementation targets the behavior introduced in Hyperswitch PR #11499.

## Current Behavior

The UCS Authorize request already carries `authentication_data`, including the
3DS version, ECI, CAVV, DS transaction ID, transaction status, and exemption
indicator. The Stripe transformer does not consume this data. It only maps
`auth_type` to `request_three_d_secure=any|automatic`.

Hyperswitch treats these as mutually exclusive paths:

- completed external authentication: forward the supplied 3DS evidence;
- no external authentication: ask Stripe to apply its normal 3DS policy.

## Design

Introduce a typed Stripe authentication representation with two variants:

1. `External3ds`, flattened into Stripe's external-3DS form fields;
2. `Request3ds`, serialized as the existing `request_three_d_secure` field.

For card Authorize requests, `authentication_data` takes precedence over
`auth_type`. When external data is present, UCS will serialize:

- `payment_method_options[card][three_d_secure][version]`
- `payment_method_options[card][three_d_secure][electronic_commerce_indicator]`
- `payment_method_options[card][three_d_secure][cryptogram]`
- `payment_method_options[card][three_d_secure][transaction_id]`
- `payment_method_options[card][three_d_secure][ares_trans_status]`
- `payment_method_options[card][three_d_secure][exemption_indicator]`
- `error_on_requires_action=true`

`request_three_d_secure` will not be serialized on that path. When
`authentication_data` is absent, the existing `auth_type` mapping and request
shape remain unchanged.

The CAVV is mandatory for Stripe external 3DS. UCS will return a structured
missing-field error if `authentication_data` is supplied without a CAVV rather
than sending an incomplete external-authentication request.

Exemption indicators `LowRiskProgram` and `LowValue` map to Stripe's
`low_risk`; unsupported exemption values are omitted, matching Hyperswitch.

## Scope

The change is limited to Stripe card Authorize request construction. It does
not alter tokenization, recurring payments, SetupIntent behavior, connector
response parsing, or comparator normalization.

## Error Handling

Invalid or incomplete external-3DS input fails before the connector call with
the existing structured integration error model. Ordinary card requests that
do not carry `authentication_data` retain their current behavior.

## Testing

Focused transformer tests will verify:

1. Complete external-3DS input serializes every expected Stripe field.
2. External-3DS requests omit `request_three_d_secure`.
3. Requests without external authentication preserve `automatic` and `any`.
4. Missing CAVV returns a clear missing-field error.
5. Formatting, targeted tests, and Clippy pass before the pull request is
   opened.

## Delivery

Development happens in an isolated worktree created from the latest
`origin/main` because the existing `connector-service-02` checkout contains
unrelated changes. The pull request will target
`juspay/hyperswitch-prism:main` and reference the observed shadow diff and
Hyperswitch PR #11499.

## Non-goals

- Suppressing the difference in the comparator.
- Changing Stripe's response or error mapping.
- Refactoring unrelated payment-method transformations.
- Modifying the existing dirty checkout.
